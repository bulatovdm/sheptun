# Analyze replacements (skill-версия)

То же, что CLI `sheptun analyze-replacements`, но модель — субагенты Claude Code.
Промпты, окна контекста, валидация и запись — общий код с CLI (`skill_analyzer.py`,
переиспользует `log_analyzer.py`).

**Прогон идёт по всему логу до конца.** Один запуск — полный проход. Чекпоинт пишется
после каждого батча, поэтому прерванный запуск продолжится с того же места.

## Конфигурация

Дефолты — в `config.yaml` рядом с этим файлом, прочитай его в начале прогона.
Аргументы пользователя перекрывают конфиг: `сонетом` → `subagent_model=sonnet`,
`заново` / `с начала` → `--full`, `сбрось чекпоинт` → шаг «Сброс».

Субагент — тип `replacement-batch` (`.claude/agents/replacement-batch/AGENT.md`).
Его `effort` задаётся во frontmatter агента: Agent tool такого параметра не принимает.

## Процедура

### 1. План

```bash
python -m sheptun.skill_analyzer plan \
  --batch-size <batch_size> --context <context_lines> --min-freq <min_freq> \
  > tmp/skill_plan.json
```

`--full` — если просили начать заново (с самых свежих окон).

В ответе: `start_position`, `full_total` и `batches[]` (`index`, `end`, `task` — путь
к файлу задания). Обход от свежих строк к старым; позиция считается от конца лога.

**Файлы заданий не читай** — они большие и нужны только субагенту. Оркестратор
оперирует путями, чтобы текст лога не проходил через его контекст.

Если `batches` пуст — лог разобран целиком, скажи одну строку об этом и заверши.

### 2. Прогон до конца

Иди по `batches[]` группами по `concurrency`. Каждую группу запускай **одним сообщением**
(все агенты сразу, параллельно): `subagent_type: "replacement-batch"`,
`model` из конфига, `run_in_background: false`, промпт:

```
Проанализируй батч и запиши найденные правила.

1. Прочитай файл <task> и выполни задание из него.
2. Запиши результат (только JSON-массив) в tmp/skill_reply_<index>.json.
3. Выполни:
   python -m sheptun.skill_analyzer commit --reply tmp/skill_reply_<index>.json --position <end> --total <full_total>

Верни одно слово: done.
```

`<full_total>` — из плана.

Правила в `replacements.yaml` и чекпоинт пишет сам субагент — записи сериализуются
файловой блокировкой, параллельные батчи друг друга не затирают.

Финальный текст субагентов не разбирай — он ничего не значит, запись происходит внутри их
собственного `commit`.

После каждой группы выполни ровно одну команду и покажи её вывод пользователю:

```bash
python -m sheptun.skill_analyzer status --total <full_total>
```

Она печатает строку прогресса:
`[окна 1425/80695, осталось 79270] правил за прогон: 5`

Это единственное, что ты пишешь между группами: своих сводок, списков найденных правил
и разбора ответов агентов быть не должно. Вывод самих субагентов до терминала не доходит,
поэтому прогресс показывает именно эта команда.

**Если позиция не дошла до `end` последнего батча группы** — значит кто-то из агентов не
добрался до `commit` (упёрся в лимит ходов). Не перезапускай агентов: их ответы уже лежат
в `tmp/skill_reply_<index>.json`. Досчитай пропущенные батчи сам, по возрастанию `index`:

```bash
python -m sheptun.skill_analyzer commit --reply tmp/skill_reply_<index>.json --position <end> --total <full_total>
```

Если файла ответа нет вовсе — пропусти этот батч, закоммить остальные и иди дальше;
чекпоинт двигается только вперёд, а незакрытый кусок подберёт следующий прогон.

**Продолжай, пока батчи не кончатся.** Не останавливайся после первой группы.

Полный проход по логу — это тысячи батчей, и такой объём согласован самим запуском скилла:
пользователь выбрал его сознательно. Поэтому работай молча до конца — не переспрашивай,
не предлагай сузить прогон, не считай расход. Вопросов пользователю по ходу прогона не
задавай (никакого AskUserQuestion): решение уже принято на старте.

Прервать прогон можно только по двум причинам:

1. **Пользователь явно сказал остановиться** — тогда сразу стоп, без уточнений.
2. **Техническая поломка** — например, `commit` падает с ошибкой на батчах подряд.
   Тогда одна строка о том, что сломалось, и стоп.

**Заполнение контекста в этот список не входит.** Не следи за своим контекстом, не прикидывай,
насколько его хватит, и не останавливайся «пока не поздно» — ты не можешь оценить это верно,
а ранняя остановка просто теряет часть прогона. Автокомпакт справится сам: твой контекст —
это лишь короткие строки прогресса, задания читают субагенты. Запускай следующую группу,
пока батчи не кончились.

### 3. Конец

Прогон заканчивается, когда кончились батчи. Не завершай его по своему усмотрению раньше —
ни «контекст на исходе», ни «обработали достаточно» поводом не являются.

(Если сессию всё же оборвёт извне — чекпоинт сохранён после каждого батча, и следующий
запуск скилла продолжит ровно с того места. Но это исход, а не цель.)

В конце — одна строка: сколько правил добавилось в `replacements.yaml`
(`git diff --stat src/sheptun/config/replacements.yaml`). Больше ничего: ни таблиц,
ни списков кандидатов, ни статистики по батчам, ни советов, что запускать дальше.

### Сброс

```bash
python -m sheptun.skill_analyzer reset
```

## Границы

- Не коммить и не пушить — пользователь ревьюит `replacements.yaml` сам.
- Не редактируй промпты в `src/sheptun/prompts/`.
- Не оценивай качество правил и не предлагай свои: правила приходят только от субагентов
  и проходят валидацию внутри `commit`.
